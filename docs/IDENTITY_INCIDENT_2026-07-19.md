# Identity Fork Incident — 2026-07-19

## Summary

On 2026-07-19, an existing administrator opened TierList+ from the same Chrome installation used
previously, but the browser no longer presented a valid TierList+ session cookie. The browser still
remembered its previous identity in local storage.

The client treated any failed session check as a first visit and silently created a new anonymous
`User` and `Device`. The original administrator account and its data remained intact, but the newly
created user had the default `USER` role, so the administrator appeared to have lost access.

## Impact

- One empty duplicate user was created.
- The affected browser resolved to the duplicate `USER` account instead of the existing `ADMIN`.
- No templates, rankings, spaces, memberships, ballots, or drafts were lost.
- The original administrator account and its linked devices were not deleted or revoked.

## Timeline

Times below are based on production database and container records.

- 2026-02-27: Original user was created.
- 2026-03-11: Platform roles and administrator RBAC were deployed.
- 2026-07-18: Production app container restarted.
- 2026-07-19 14:23: Last recorded activity from an existing linked Chrome device.
- 2026-07-19 17:45: Duplicate anonymous user and `Device 1` were created.
- 2026-07-21: Incident investigated; the active browser device was relinked to the original user and
  the empty duplicate user was removed.
- 2026-07-21: Revised identity bootstrap, direct recovery, merge hardening, and audit events were
  deployed.

## Confirmed Root Cause

The confirmed application defect was the client transition in `ensureUserIdentity()`:

1. Read the identity remembered in local storage.
2. Call `GET /api/users/session` to validate the HTTP-only cookie.
3. If the endpoint returned `401`, immediately call `POST /api/users`.
4. Replace the remembered local identity with the new anonymous user and device.

The remembered identity was therefore read but not used to prevent accidental account creation.
A recoverable session problem became a silent account fork.

## Trigger: Not Proven

The exact reason the original cookie was unavailable cannot be reconstructed because the previous
implementation did not record session rejection reasons or identity events.

Possible triggers include:

- browser site-data or cookie cleanup;
- opening a different site origin or Chrome profile;
- a session secret change without retaining the previous secret;
- browser/profile storage migration failure.

Chrome released updates shortly before the incident, but no evidence showed that an update removed
the TierList+ cookie. A Chrome update should not be treated as the root cause without direct browser
storage evidence.

## Recovery Performed

Before changing production:

1. Both user records and all linked devices were inspected.
2. The duplicate account was confirmed to own no application resources.
3. A compressed pre-recovery database backup was created.

The existing recovery API was then used to merge the empty duplicate into the original account.
The active browser device was retained and moved to the surviving administrator user. Verification
confirmed:

- the device resolved to the original user;
- the surviving role was `ADMIN`;
- the duplicate user no longer existed;
- all original resources remained present.

## Corrective Changes

The identity model now enforces these rules:

- A missing or invalid cookie does not create a user when local storage remembers an identity.
- The browser enters an explicit recovery-required state.
- Starting a new empty workspace requires an explicit confirmation.
- A one-time link code can attach an unauthenticated browser directly to its target user, avoiding a
  temporary user and later merge.
- Auth failures have structured reasons: missing cookie, invalid token, missing device, or revoked
  device.
- Account merges preserve the higher platform role and retain the target nickname when present.
- User creation, direct device linking, and account merges create append-only `IdentityEvent` rows.
- Identity creation and recovery attempts are rate-limited.

The normative design is documented in [IDENTITY.md](IDENTITY.md).

## Operator Runbook

When a user reports lost ownership or role access:

1. Do not immediately promote the currently visible user.
2. Record the current user ID and active device ID shown by the client.
3. Inspect candidate users, roles, device activity, and ownership counts in production.
4. Determine whether this is a role change, revoked device, missing session, or duplicate user.
5. Prefer a normal one-time recovery link generated by an existing linked browser.
6. If production intervention is necessary, take a database backup first.
7. Use the recovery API or `mergeAccountIntoTarget`; avoid ad hoc deletes or partial reassignment.
8. Verify the surviving user, role, active device, resource counts, and duplicate-user removal.
9. Confirm the app, database, monitoring timer, and public session endpoint remain healthy.

Never log or commit session cookies, session secrets, recovery codes, or database credentials.

## Remaining Risk

If a browser loses both its HTTP-only cookie and all local storage, the application cannot
distinguish it from a genuine first visit. Optional verified email or passkey recovery is still
needed for durable recovery when all browser-local state is gone.
